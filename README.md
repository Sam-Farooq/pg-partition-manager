# pg-partition-manager

Declarative range partition lifecycle for PostgreSQL 16, written as PL/pgSQL
functions. It creates the partitions a table will need before it needs them,
attaches a table that already holds rows without holding ACCESS EXCLUSIVE
through a table scan, takes partitions off the end into an archive schema, and
moves rows out of a default partition into the partition they belong in.

There is no background worker, no scheduler and no extension to install. psql
loads nine files, and something outside the database calls the functions: cron,
pg_cron, an application, a person at a prompt. Version 0.13.2.

```bash
psql -v ON_ERROR_STOP=1 -f sql/install.sql
```

```sql
CREATE TABLE events (
    id    bigint GENERATED BY DEFAULT AS IDENTITY,
    at    timestamptz NOT NULL,
    body  text
) PARTITION BY RANGE (at);

SELECT ppm.register_set('events', 'at', 'day', premake := 3,
                        retention := interval '30 days');
NOTICE:  public.events registered: day partitions, 3 ahead, retention 30 days

SELECT ppm.create_ahead('events', '2026-03-17 11:00+00');
NOTICE:  public.events created 4 partition(s)

SELECT child, lower_bound, upper_bound, total_bytes FROM ppm.partitions('events');
      child      |      lower_bound       |      upper_bound       | total_bytes
-----------------+------------------------+------------------------+-------------
 events_20260317 | 2026-03-17 00:00:00+00 | 2026-03-18 00:00:00+00 |        8192
 events_20260318 | 2026-03-18 00:00:00+00 | 2026-03-19 00:00:00+00 |        8192
 events_20260319 | 2026-03-19 00:00:00+00 | 2026-03-20 00:00:00+00 |        8192
 events_20260320 | 2026-03-20 00:00:00+00 | 2026-03-21 00:00:00+00 |        8192
```

That session ran with the client in UTC. The bounds are instants and do not
move with the client; only their rendering does, which is the subject of
[Boundaries are cut in a stored zone](#boundaries-are-cut-in-a-stored-zone).

22 functions, 2 tables, 2 views, 1704 lines of SQL. 180 pgTAP tests over 10
files. CI runs them against a `postgres:16` service container; locally they run
against any server psql can reach.

## What each function does, and what it costs

| Call | Runs | Lock, at its worst |
|---|---|---|
| `ppm.register_set(parent, key, granularity, ...)` | validation and one upsert | row level |
| `ppm.create_ahead(parent, as_of, dry_run)` | `CREATE TABLE ... PARTITION OF` per missing period | brief ACCESS EXCLUSIVE on the parent, plus a scan of the default partition if there is one |
| `ppm.prepare_for_attach(child, key, lo, hi, dry_run)` | `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT` | SHARE UPDATE EXCLUSIVE on the child, for the length of a scan of it |
| `ppm.attach_prepared(parent, child, lo, hi, dry_run)` | `ATTACH PARTITION` | brief ACCESS EXCLUSIVE on the parent, plus the default partition scan |
| `ppm.apply_retention(parent, as_of, dry_run, allow_empty)` | `DETACH`, then `SET SCHEMA` or `DROP TABLE` | ACCESS EXCLUSIVE on the parent per partition |
| `ppm.drain_default(parent, max_ranges, dry_run)` | create, move, constrain, attach, in one transaction | ACCESS EXCLUSIVE on the parent until the call commits |
| `ppm.retention_script(parent, as_of)` | nothing. Returns text | none |
| `ppm.index_script(parent, name, columns, is_unique)` | nothing. Returns text | none |

Every function that acts takes `dry_run` and returns the statements it ran, or
with `dry_run` the statements it would have run. Every one of them writes what
it did to `ppm.run_log`, so the history is a table rather than a log file:

```sql
SELECT ran_at, action, target_name, rows_moved FROM ppm.recent_runs;
SELECT * FROM ppm.managed;
```

The log is written inside the caller's transaction, which means a run that
rolls back leaves no trace of itself. That is deliberate. The log says what
happened, not what was attempted.

## The lock, measured

`ATTACH PARTITION` has to prove that every row in the new partition is inside
its bounds. If it cannot prove that from the catalogue it reads the table, and
it does the reading while holding ACCESS EXCLUSIVE on the parent, which blocks
readers of every other partition too. A validated CHECK constraint that implies
the bounds turns the proof into a catalogue lookup.

`test/05_attach.sql` measures this with `pg_stat_all_tables.seq_scan` across
2,000 row tables:

| Statement | Scans of the child | Scans of the default partition |
|---|---|---|
| `ATTACH PARTITION` with no CHECK | 1 | 1 |
| `ADD CONSTRAINT ... NOT VALID` | 0 | not involved |
| `VALIDATE CONSTRAINT` | 1 | not involved |
| `ATTACH PARTITION` after that | 0 | 1 |

The two middle statements name the child only, which is not a partition of
anything yet, so the parent and its default partition are not in their way.
They are measured one statement at a time, and the statements are taken from
`prepare_for_attach()`'s own dry run and run with `\gexec`, so the measurement
cannot drift from what the function does.

**The scan does not go away. It moves.** Both routes read the table once. The
difference is the lock it is read under: ACCESS EXCLUSIVE on the parent in the
first row of that table, SHARE UPDATE EXCLUSIVE on the child alone in the
third, which lets reads and writes through while it runs. That is the whole
trade, and what it costs is two statements and two lock acquisitions instead of
one, plus a CHECK constraint left behind on the partition for ever.

The default partition's scan is in both routes and cannot be prepared away: the
server has to prove the default holds no row belonging in the new range. The
one way out is a CHECK constraint on the default that excludes the range, which
is measured in the same file.

That measurement is also the reason that file commits instead of rolling back.
Table statistics are accumulated per backend and flushed when a transaction
ends, so a count read inside the same transaction as the work is the count from
before the work.

## Two functions that only return text

```
ERROR:  25001: ALTER TABLE ... DETACH CONCURRENTLY cannot run inside a
        transaction block
ERROR:  25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

A function body is always inside a transaction block, so no function in this
repository can run either statement. There is no flag that changes it.
`ppm.retention_script()` and `ppm.index_script()` write those statements out
instead, and `test/06_retention.sql` asserts the 25001 rather than taking the
documentation's word for it.

`ppm.index_script()` writes the three part sequence that adds an index to a
partitioned table without locking it out of use: `CREATE INDEX ... ON ONLY` the
parent, `CREATE INDEX CONCURRENTLY` on each partition, then `ALTER INDEX ...
ATTACH PARTITION` for each. The parent index stays invalid until the last
attach. Run it the way it is meant to be run, which is also how the test runs
it:

```sql
SELECT line FROM ppm.index_script('events', 'events_at_idx', 'at') AS s(line)
 WHERE line NOT LIKE '--%' \gexec
```

`test/08_index_script.sql` executes exactly that and then asserts the parent
index came out `indisvalid` with one child index attached per partition. A
script that is never run is a script that is plausible rather than correct.

## Draining the default partition is the only order that works

A default partition is the thing that stops an INSERT failing when no partition
matches, and it is also what makes every later `CREATE TABLE ... PARTITION OF`
and every `ATTACH` scan it. Worse, once it holds rows for a range, the
partition for that range cannot be created at all:

```
ERROR:  23514: updated partition constraint for default partition
        "events_default" would be violated by some row
```

So the rows have to leave the default before the partition exists, which means
the table they go into cannot be a partition while they are moving. One order
survives that:

1. `CREATE TABLE ... (LIKE parent INCLUDING DEFAULTS INCLUDING CONSTRAINTS ...)`
2. `WITH moved AS (DELETE FROM default WHERE key >= lo AND key < hi RETURNING ...)
   INSERT INTO target ...`
3. `ADD CONSTRAINT ... NOT VALID`, `VALIDATE CONSTRAINT`
4. `ATTACH PARTITION`

`ppm.drain_default()` does all four in its own transaction, so an interrupted
call leaves nothing half done. `max_ranges` defaults to 1 because the attach
takes ACCESS EXCLUSIVE on the parent and a function cannot commit, so the lock
is held until the call returns: ten ranges in one call is ten times the lock.

What that costs: a default partition with a year of rows in it needs a lot of
calls, and every call reads the whole default again to find the next period.
The query that finds it is `SELECT DISTINCT` over the partition key with no
index that can help, because the question is about every row. A single call
that handled everything would read the default once. It would also hold the
parent locked for the whole of it.

The 23514 above is caught and re-raised as 55000 naming the default partition
and the function to call. Two other server errors are rewritten the same way:

| What the server says | What this says instead |
|---|---|
| 23514 `updated partition constraint for default partition ... would be violated` | 55000 `the default partition public.events_default holds rows in [...)`, hint: `ppm.drain_default()` |
| 42P17 `partition "x" would overlap partition "y"` | the same, raised before the DDL runs, naming the partition in the way and the range that collided |
| 42P07 `relation "x" already exists` | `public.events_20260317 already exists and is not a partition of public.events` |

## Boundaries are cut in a stored zone

`date_trunc('day', some_timestamptz)` truncates in the session's `TimeZone`.
The first version of `ppm.bounds_for()` did that, the server it was written
against runs `Asia/Karachi`, and every boundary came out five hours early.
The tests caught it and the commit that fixed it is in the history.

Boundaries are now cut on a `timestamp` taken in `bound_tz`, which is stored
per partition set and defaults to UTC, and converted back. A boundary is
therefore a property of the table rather than of whoever is connected, and a
backfill run from a laptop writes partitions that line up with the ones the
scheduled job wrote.

Asking for boundaries in a named zone cuts them at local midnight there, which
is what a daily report in that zone means by a day. In a zone that observes
daylight saving, one daily partition a year is 23 hours wide and another is 25.
That is correct and it is worth knowing before anyone writes
`upper_bound - lower_bound`.

Two smaller consequences, both tested:

- `ppm.partition_bounds()` reads bounds back by parsing
  `pg_get_expr(relpartbound)`, which renders its literals in the session zone.
  The round trip through a cast recovers the instant, so the answer does not
  change when the client does.
- Adding `bound_tz` to two functions meant dropping them rather than replacing
  them. A new argument with a default produces a second overload, and then a
  short call matches both and the server refuses it as ambiguous. The two
  `DROP FUNCTION IF EXISTS` lines at the top of `sql/002_bounds.sql` are the
  upgrade path and stay there.

## What it refuses to do

- **A `date` or plain `timestamp` partition key.** `register_set()` rejects it
  by name, with the type in the message. The bound literal and the trip through
  `AT TIME ZONE` both differ, and a half-supported date key would produce
  boundaries that look right until somebody set a session `TimeZone`.
- **Any interval other than day, week or month.** A partition scheme has to
  tile the key space with no gap and no overlap. Two months does not divide a
  year and 36 hours does not divide anything.
- **List and hash partitioning, expression keys, and multi-column keys.** Each
  is refused with its own message, because the alternative is parsing a
  partition bound that means something else.
- **Deciding whether a constraint written by somebody else implies the
  bounds.** `attach_prepared()` looks for the constraint this manager writes,
  by name, validated, mentioning both bounds. A hand-written equivalent is not
  recognised. That is a false negative on purpose: predicate implication is the
  planner's job, and a function that guesses at it would sometimes promise a
  scan is skipped when it is not.
- **Trimming rows at the retention cutoff.** Only whole partitions are removed,
  so the oldest data can live up to one partition longer than the window says.
  Trimming would make retention a `DELETE`, which is what partitioning is for
  avoiding.
- **Emptying a set.** A retention window that would remove every partition
  raises instead, because that is what days-instead-of-months looks like.
  `allow_empty := true` says otherwise.
- **Scheduling itself.** No background worker, nothing to operate, nothing that
  keeps running after a crash. The cost is that forgetting to call
  `create_ahead()` on a set with no default partition means an INSERT fails at
  midnight with `no partition of relation "events" found for row`.

## Tests

```bash
make pgtap          # fetch pgTAP 1.3.3, verify its sha256
make test           # build a database, run the suite, drop it
make lint           # conventions, no database needed
```

180 tests in 10 files. `test/run_tests.sh` builds `pg_partition_manager_test`,
loads pgTAP and `sql/install.sql` into it, runs each file in its own psql
session, and drops the database again. It refuses to touch a database that
already exists unless `TEST_DB_REUSE=1`, and it says what it tried to connect
to when nothing answers:

```
$ PGHOST=127.0.0.1 PGPORT=1 PGUSER=app test/run_tests.sh
no PostgreSQL server answered.

  host     127.0.0.1
  port     1
  user     app
  database postgres (set MAINT_DB if that one does not exist)

libpq said:
  psql: error: connection to server at "127.0.0.1", port 1 failed: Connection refused
```

| File | Tests | What it is about |
|---|---|---|
| `00_install.sql` | 9 | the objects exist, the version agrees with `VERSION`, `install.sql` loads twice |
| `01_bounds.sql` | 23 | boundaries, names, the session zone, the 63 byte identifier limit |
| `02_inspect.sql` | 19 | reading bounds out of the catalogue, and the shapes that are refused |
| `03_register.sql` | 21 | validation. 11 of the 21 are refusals |
| `04_create_ahead.sql` | 19 | tiling with no gaps, idempotence, overlaps, the default partition |
| `05_attach.sql` | 17 | the scan measurements above, one statement at a time |
| `06_retention.sql` | 25 | cutoffs, archiving, the empty-set guard, the 25001 |
| `07_drain_default.sql` | 21 | rows moving, and `create_ahead()` failing before and working after |
| `08_index_script.sql` | 14 | the script, run with `\gexec`, and the index coming out valid |
| `09_log.sql` | 12 | the log, `recent_runs`, `managed`, and a dropped parent |

Three facts about the suite worth knowing before trusting it:

- **It needs a server.** There is no mock. Every assertion is against a real
  PostgreSQL 16, which is what makes them worth having: the claims are about
  what the server does with locks, bounds and constraints.
- **No network beyond that.** No cloud, no key, no fixture downloaded at test
  time. `make pgtap` fetches pgTAP once, over https, pinned by tag and by
  sha256, into `.pgtap/`, which is gitignored. The suite itself opens nothing.
- **Two paths have no test, and both need a second session.** The
  `lock_not_available` handler in `apply_retention()` and the
  `serialization_failure` handler in `drain_default()` fire when another
  connection holds a lock or writes to the default partition while a call is
  running. The runner is one psql session at a time, so neither has been
  exercised. They are four lines each and they are not covered.

`test/lint.sh` is the other half, and it has teeth rather than opinions. It
fails the build if a function does not pin `search_path`, if a function has no
`COMMENT`, if `install.sql` has drifted out of step with the files in `sql/`, if
anything in `sql/` is a plain `CREATE TABLE` rather than `IF NOT EXISTS` (which
would break the second install), if a test file has no plan or no `finish()`,
if a test file runs outside a transaction without saying why, if an assertion
cannot fail, if `VERSION` and `ppm.version()` and this file disagree, or if a CI
action is not pinned to a tag.

There is no SQL formatter here. The things worth failing a build over are the
ones a formatter does not look at, and one that rewrote PL/pgSQL bodies would
be worse than none.

## Everything the Makefile does

```
make install    load sql/install.sql into the database psql would connect to
make uninstall  drop the ppm schema from that database
make test       build pg_partition_manager_test, run the pgTAP suite, drop it
make lint       convention checks over sql/, test/ and the version string
make pgtap      fetch pgTAP 1.3.3 into .pgtap
make clean      remove .pgtap and test/out
```

Connection comes from `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`.
Nothing is started for you and nothing has a default host.

## Layout

```
sql/
  install.sql           one transaction, every file below in order
  001_schema.sql        schema ppm, the registry, the run log, ppm.version()
  002_bounds.sql        bounds_for(), partition_name(), the stored zone
  003_inspect.sql       bounds read back out of pg_class.relpartbound
  004_register.sql      register_set(), and everything it refuses
  005_create_ahead.sql  the partitions a set will need
  006_attach.sql        prepare_for_attach(), attach_prepared()
  007_retention.sql     apply_retention(), retention_script()
  008_drain_default.sql moving rows out of the default partition
  009_index_script.sql  the online index sequence, as text
test/
  run_tests.sh          builds a database, runs each file, drops it
  lint.sh               conventions, no database
  fetch-pgtap.sh        pinned tarball, sha256, one loadable file
  fixtures.sql          hand written tables for the suite to work on
  0*.sql                the ten test files
```

Nothing in this repository has been run against a production system, and no
number in it came from one. The four scan counts are produced by
`test/05_attach.sql` on whatever server you point it at; the row counts in the
examples are the fixtures in `test/fixtures.sql`, written by hand.
